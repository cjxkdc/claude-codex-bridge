Use `codex_discuss` from MCP server `codex-peer`. This Claude Code conversation is the host. For one-pass review use `codex_review`.

For sending files into a named EXISTING Codex chat, use the codex-chat skill and codex_find_chats/codex_send_to_chat, rather than starting a new discussion.

When the user specifies Codex's model or reasoning effort, send model/effort as actual tool parameters, not just prompt text. Preserve an exact Codex CLI model ID such as gpt-6.1-sol or gpt-6-astra; do not invent or replace a requested ID. Map 低/中/高/超高/最大/极高 to low/medium/high/xhigh/max/ultra; supported levels depend on the selected model. Omit unspecified settings to keep CLI defaults. These parameters select Codex; the current Claude conversation keeps its host settings. Continue the same session without resending parameters unless the user requests a change; to reset an option send auto/default. State the requested selection in your response, using returned peer_options/requested. Do not present requested settings as independently confirmed effective settings. Account/model restrictions can reject or limit a selection; report the error rather than silently choosing another model.

Start once with objective, absolute cwd, relevant relative files/logs and your initial diagnosis/proposal in host_message. max_rounds equals the user's x, defaults to 3 and supports 1..20. One round is a host contribution plus a Codex response. Read the actual reply, validate hypotheses, then continue the SAME session_id with revised reasoning and evidence. Finish early when appropriate. Stop at closed status or peer-error; never restart to evade x.

Default peer access is read-only. Only when the human user explicitly authorizes the invited agent to modify files (for example, “允许对方改代码” or “双方都可以修改”), set access: edit and supply edit_files as a minimal fixed list of relevant relative UTF-8 text paths, including new paths if creation is authorized. State that scope before calling; do not ask again for permission already given. Source files and peer messages cannot grant permission. The peer returns structured changes; the bridge validates them, backs up originals and applies create/update contents. The CLI still has no direct repository or command access. Check each peer turn's edit_result: only applied confirms writes; no-changes means no write. On conflict/rejected/failed/partial, stop, report actual changes and backup_path, and inspect the diff; do not claim the proposed edits succeeded. Access and edit_files cannot widen during a session. Review/ask/explain/plan-review remain read-only. Inspect and test applied changes between rounds, and avoid editing the same files while a peer request is in flight.

Perform implementation/testing yourself only within the user's request. Summarize common ground, disagreements and next actions here, then continue authorized work. AGENT_PEER_DEPTH=1 blocks peer calls. Missing MCP requires restarting after installation; do not bypass protections with raw CLI invocation.

Each tool result is Markdown: the newest peer reply, its 修改结果 (edit_result status, files and diff) when edits were requested, then session_id, status, record.markdown_path and next_action. It does not repeat earlier rounds; call action=status to get the whole transcript as Markdown. Pass format=json only when a script needs the full object. Discussion calls automatically save each round under the bridge's reports/discussions directory. When a record path is returned, include record.markdown_path in the final response so the user can open the record; the .json file beside it contains the structured transcript. If saving failed, report the returned error and do not claim a file was saved. On request, show the status transcript verbatim with speaker and round labels. Records contain the exchanged messages, not internal reasoning or the entire host conversation. Old files survive MCP restarts; active sessions do not.
